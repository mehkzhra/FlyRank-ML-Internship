Which content pages should be reviewed first?

An honest, public-safe comparison of a transparent rule and three classifiers for prioritizing scarce editorial review time.

Mehak Zahra · 5 September 2026 · Client-group holdout · Human-in-the-loop decision support

Abstract

This study asks which measurable content pages an editor should review first when review capacity is limited. I analyzed the 30,000-page anonymized starter slice associated with the FlyRank ML Internship dataset and defined an observed-decline proxy from the supplied 30-day comparison. I compared a transparent four-part rule score with logistic regression, a decision tree, and a random forest, using a client-group holdout so all six test clients were unseen during training. On the same 2,325-page test split, the selected random forest reached Precision@50 of 0.74 versus 0.24 for the rule baseline, while ROC AUC improved from 0.627 to 0.750. The result supports a human-reviewed triage queue; it does not show that refreshing a page causes recovery or that the model predicts future search performance.

Introduction / problem statement

A content editor cannot inspect 30,000 pages at once. The useful decision is not “will this page certainly improve?” but “which pages deserve scarce review time first?” One row represents one anonymized content page; the output is a ranked queue with reason codes.

A false positive costs editor time. A false negative can leave meaningful decline unreviewed. Precision@50 asks what share of the first 50 recommendations carries the observed-decline proxy, matching a practical review batch. ROC AUC and average precision test whether discrimination extends beyond that one cutoff.

Intended useA content editor or SEO analyst reviews the queue, checks the real page and business context, then chooses refresh, expansion, CTR review, engagement review, or monitoring. The model never publishes or deletes content.

Data

The analysis uses content_refresh_anonymized.csv, the bundled public-safe starter release: 30,000 rows × 44 fields at one-row-per-content-page grain. Its measures include trailing 90-day search and engagement aggregates and two adjacent 30-day comparison windows.

Repository documentation connects this slice to release flyrank_pseudonymized_warehouse_release_v20260703, exported 3 July 2026. The full warehouse contains 78,835,655 daily content-performance rows spanning 27 January 2025 through 30 June 2026.

Scope boundaryThis experiment did not query the full fact table and is not a 79-million-row benchmark. It analyzes the 30,000-page starter slice. The larger release is credited and documented only as the data ecosystem from which the internship materials derive.

All 30,000 rows passed the reference preparation filters: positive trailing impressions, content age of at least 90 days, and a unique content ID. The full sample contains 16,262 proxy-positive pages (54.21%). The held-out test set contains 2,325 pages across six client groups, including 909 positives (39.10%).

Public-safety exclusions

No raw client names, domains, URLs, titles, keywords, or queries are used or displayed. Pseudonymous IDs support grouping only. Direct label fields and components—trend_direction, trend_pct, and the last/previous 30-day impression, click, and session fields—are excluded from the feature matrix.

Methodology

Label and assumption

The binary proxy is positive when supplied trend_direction is down: last-30-day impressions are more than 20% below the preceding 30 days. It describes observed current-window decline, not a future outcome or refresh success. The modest assumption is that current decline plus measurable opportunity can help prioritize human review.

Features

The pipeline builds 52 encoded columns from 18 numeric and eight categorical fields. Inputs cover search-market attributes, content length, logged 90-day activity, active-day counts, age and update recency, CTR, average position, engagement/scroll/AI-traffic rates, and categorical tiers. Numeric missing values become zero after type coercion; categorical blanks become unknown.

Baseline and models

The transparent baseline is 40% visibility percentile + 30% freshness-risk percentile + 25% position opportunity + 5% depth gap. Candidate models are logistic regression, a depth-limited decision tree, and a 200-tree random forest. Seed 42 is fixed. Selection maximizes Precision@50, with average precision and ROC AUC as tie-breakers.

Validation and leakage checks

The split holds out 20% of client groups: 26 clients (27,675 rows) train the models; six clients (2,325 rows) form the test set. No client crosses the boundary. Baseline and models use exactly those test rows.

Residual leakage riskTrailing-90-day aggregate features overlap the two 30-day periods defining the proxy. They do not directly encode the label, but this overlap prevents a clean future-prediction interpretation. The valid framing is contemporaneous triage.

Results

The random forest places 37 observed-decline pages in its first 50, compared with 12 for the baseline: a 50-point absolute gain and 3.08× baseline precision at the chosen operating point.

Limitations & honest framing

  1. The study uses a 30,000-page slice, not the 78.8M-row daily fact table; representativeness is unproven.
  2. The target is a contemporaneous operational proxy—not future performance or refresh success.
  3. Trailing-90-day features overlap the proxy windows, preventing a leakage-clean forecast claim.
  4. Model selection and reporting share one grouped holdout; this can make the result optimistic.
  5. The client panel is unbalanced, and zeros can mix no activity with unavailable tracking.
  6. Feature importance describes fitted-model behavior, not why a page declined.
  7. No causal claim is made. A prospective experiment is required to test whether acting improves outcomes.

Ranked recommendations

  1. Review high-confidence, high-exposure candidates first. Begin with 50; verify the decline and editorial context before changing content.
  2. Route by reason code. Inspect snippet/intent fit for visible low-CTR pages, coverage for thin pages, and experience/content fit for low-engagement pages.
  3. Keep a human approval gate. Never auto-publish, prune, redirect, or promise recovery from this score.
  4. Capture review outcomes. Record accepted/rejected recommendations, action, review cost, and later outcomes to build an intervention-aware label.
  5. Upgrade validation before production. Use non-overlapping historical features and future targets, then reserve an untouched time-and-client confirmation set.
